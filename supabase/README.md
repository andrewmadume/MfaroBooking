## Runtime

The app's `lib/supabase-database.ts` connects over HTTPS to the deployed `mfarobooking-db` Edge Function. This preserves the existing prepared-statement data layer without adding TCP database credentials to the Worker. Existing D1 schema/migrations remain only for offline/local development when no Supabase settings are supplied.

The connection requires three **server-only** settings:

- `SUPABASE_GATEWAY_URL`
- `SUPABASE_GATEWAY_ANON_KEY`: the project legacy anon JWT, used for the Edge gateway's built-in JWT verification.
- `MFARO_DATABASE_KEY`: a separate random 256-bit app key. The function compares its SHA-256 hash with an enabled entry in `mfarobooking_private.app_keys` before processing any query.

The current workspace has these settings in ignored `.dev.vars`. They have also been saved as secrets in the existing private Sites runtime configuration. They are intentionally absent from GitHub and source archives. A fresh clone must receive them through its deployment secret store. Do not copy a Supabase service-role key into the browser or disable JWT verification to work around a configuration failure.

## Access boundaries

- Application tables live in the non-exposed `mfarobooking` schema. Neither `anon` nor `authenticated` has schema/table access.
- Every application table has RLS enabled. The narrowly scoped, non-login `mfarobooking_runtime` role receives only SELECT/INSERT/UPDATE, plus DELETE on expiring rate-limit entries. End users never receive this role.
- The app's API continues to enforce the existing tenant, role and branch permissions before preparing queries. ChatGPT remains the identity provider; this change does not migrate accounts to Supabase Auth.
- The Edge Function obtains its database URL from Supabase's built-in server environment. It validates the private key, checks an exact allowlist of application query templates, and switches to the restricted role before running application SQL. It cannot be used as a general SQL endpoint.
- `allowed.ts` is generated by `npm run db:queries`. `npm test` and `npm run build` regenerate it. After changing an application SQL template, redeploy `index.ts`, `dialect.ts` and `allowed.ts` together before deploying the changed app.
- Bound values remain separate from SQL. SQLite-compatible query templates are converted to PostgreSQL in `dialect.ts`, including parameter markers, JSON paths, reserved column names and conflict-ignore writes.
- Each HTTP batch is a PostgreSQL transaction. Mutating requests take a transaction-level advisory lock before their first app statement. Under READ COMMITTED, subsequent inventory checks observe the previous writer's committed result. This deliberately serializes writes for correctness; a higher-throughput release can replace the global lock with carefully ordered resource/tenant locks.

`test:supabase` runs the real API workflow suite against this configured project using unique fictional verification accounts. It creates persistent test fixtures in isolated workspaces, not in your real business workspace. The ordinary `npm test` suite stays local and needs no Supabase credentials.
